01The one idea

The agent loop and the model run on the host, with your privileges. Only what the agent does goes into a container.

The promise nobody makes: nothing stops the model from wanting to do something. What stops it is that the container it runs commands in cannot reach anything the policy did not grant.

02One tool call, end to end

The policy is read twice — once to tell the model what it may ask for, and again at the moment of the call. That second read is the whole reason an edit in the Policy tab lands on the very next tool call and never on one already running.

1you → browser "archive the newsletter"
2browser → server.py POST /api/chat{ agent: "health" }
3server.py → agent.py Agent(app, "health")picks the prompt, the tool set and the policy file for that subagent
4agent.py → disk reload_policy("health")first read — decides which tools the model is even offered
5agent.py → Lemonade messages + tool schemas for health only
6Lemonade → agent.py tool_call: archive_message
7agent.py → disk reload_policy("health") againfresh read from disk — your edit lands on THIS call
8agent.py compile_config() → MXCConfigurationpaths expanded, host capabilities applied, notes attached
9agent.py → wxc-exec execute(config)spawns a one-shot container and runs the command inside it
10sandbox Access is deniedoutcome: blocked — the sandbox started, the command ran, Windows refused it
11agent.py → Lemonade "REFUSED BY POLICY … do not retry"the model is told plainly, so it cannot confabulate the data
12agent.py → browser SSE: tokens + the sandbox eventyou can expand it inline and read the exact config that was sent

04What an agent actually is

Everything that used to be hardcoded now hangs off one record in core/agents.py. Switching agent swaps all three arms at once — and the Policy tab names the file it is editing, so you can watch it change.

There are two kinds. Four personas, each sealed in its own folder under vault/, and one base agent that collects what they produce and holds no data of its own.

The asymmetry is the whole exercise. A persona produces and stops; it cannot reach a calendar. The base agent collects from all four and cannot read one blood test or one bank balance. Neither can see the other's private half, and nobody wrote a rule to say so — the access was simply never granted.

Take ${vault}\health\invites out of the base agent’s paths.read and the chain breaks at sync_vaults, with Windows’ own refusal text on screen. The other three personas keep arriving. Put the line back and the next check picks it up with no restart — the fingerprint includes the policy file mtime for exactly this reason.

Two separate gates, and conflating them makes refusals impossible to explain. Does this agent have hands of this shape at all? The health agent never sees list_processes — it is not switched off, it is not part of what the health agent is. Is this particular hand switched off right now? That is policy.tools, a host-side gate, and the weakest control on the screen.

The pane and the agent read the same files by different routes, and that is deliberate. The pane says there are messages in your private folder; the agent is refused them. That gap, on screen, side by side, is the policy working — not a bug.

Why files rather than a live connection. All three reasons matter, and the first one is decisive:

The sandbox cannot reach the network for this hostLoopback is only grantable on BaseContainer, and verify.py measures that a contained process cannot reach loopback on the tiers most machines get. A mail server — local or proxied — is unreachable no matter which knob you flip. There would be no working state to flip into.
Shared live IMAP breaks at room scale Gmail caps simultaneous connections per account at around fifteen and flags many IPs hitting one account at once. One person archiving would change everyone else's inbox.
A live credential fights the injection demo There is a planted phishing email in the seed. Putting a Google app password where the agent might read it is the one thing that demo exists to punish.

07Measured limits on this hardware

From verify.py, not from anybody's expectations. Re-run it on your own box rather than trusting this list.

TierAppContainer + BFS (tier 2)
Network dialectmodern
dir through cmd Refused. Directory enumeration asks for an access an AppContainer read grant does not carry. Get-ChildItem on the same granted folder is fine, which is why the mail and record tools are PowerShell.
Delete or move a file Refused. A read-write grant carries create and write but not DELETE, so move_file cannot work here at all — even with source and destination inside one granted folder. The base agent archives by copy-and-tombstone, and the pane says so rather than hiding it.
Loopback from inside Refused, as designed. This is exactly why the model stays on the host and only tool calls go inside.
PowerShell in a sandbox Works now. It did not on the first run — STATUS_DLL_INIT_FAILED — which killed five of the nine original tools.
If a refusal does not happen when you said it would, say so out loud and go look at why. A workshop about containment that papers over a failed containment check has taught the room the opposite of the intended lesson.
